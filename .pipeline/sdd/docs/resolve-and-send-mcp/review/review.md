### summary

Merged single-pass tech review of the CODE in the F-7 aggregate diff (119 files; the ~14k lines of .pipeline/ metadata were deliberately skipped except as review input). The feature is well built: the send handler keeps bytes off reduced state, EnvelopeAssembly reuses F-6's geometry and prompt seams instead of recomputing them, the slot write is images-then-ATOMIC_MOVE in the right order, Koin/Orbit/design-token/package-layout conventions hold, and the three Stage 5 CRs (AF-1, AF-4, AF-5) are genuinely fixed where they were applied. One blocking defect: AF-1 was patched at the call site rather than at the root, so three sibling accessors in McpDispatcher.handle still throw out of the stdio read loop on a structurally-malformed JSON-RPC line — verified empirically, not inferred. One major correctness gap (a send already in flight is re-enabled by staging another annotation, making the 'second concurrent send is not reachable' invariant false) and one major plan contradiction (a corrupt slot is reported to the agent as 'nothing sent yet', not as the tool error the plan's errorState requires). Everything else is minors and nits. The nine gate decisions, the eight accepted waivers and T-13's outstanding demo were not re-litigated. | POST-CR: the one blocking and both major findings were fixed on the integration branch and re-verified against the real installDist binary; the verdict is revised from request-changes to approve-with-nits. Five minors and six nits remain open as recorded tech debt.

### techDebt

- F-4 (minor) data-handoff-api/src/desktopMain/kotlin/data/handoff/api/core/slot/FileSlotAnnotationHandoff.kt:53 — ATOMIC_MOVE protects latest.json's contents but not the publish as a whole, and nothing serializes two publishes. Concurrent publish A/B: both write the same fixed `latest.json.tmp` path (line 53-54, interleaved content), then whichever moves first runs pruneSendDirectoriesExcept(its own dir) at line 61 and deleteRecursively's the other's send directory while that publish is still writing images into it — so the surviving slot can name a directory whose frame.png and crops no longer exist, and the loser's Files.move can fail with NoSuchFileException. Today the only caller is the gated ViewModel, which is why this is minor rather than major — but F-2 is a concrete path that opens the gate, and the KDoc ('the slot either holds the previous envelope or the new one') overstates what is guaranteed. A per-publish unique tmp name (`latest.json.<sentAtMs>.tmp`) plus a mutex or a FileLock in publish() closes it.
- F-5 (minor) presentation-feature-mirror/src/commonMain/kotlin/presentation/feature/mirror/source/mirror/MirrorViewModel.kt:809 — `runCatching` at line 809 catches Throwable, which includes CancellationException. If the ViewModel is cleared (or viewModelScope is otherwise cancelled) between Preparing and Publishing, the cancellation is reported through onFailure as a send failure: a Kermit warning claiming 'Resolve & Send failed' and a `reduce { send = Failed }` attempted on an already-cancelled scope. The practical damage is limited (the reduce itself re-throws at its suspension point and the host is going away anyway), but the log lies about the cause and the pattern hides any future cancellation that matters. Rethrow it: `.onFailure { if (it is CancellationException) throw it; ... }`. Same shape, lower stakes, in AwtCropEncoder.kt:29 (a cancelled encode is reported as a null crop, i.e. a degraded payload). Everything else about the timing seams checks out: `elapsed.markNow()` is monotonic and read once at line 859, `nowMs()` is the single wall-clock read feeding both sentAtMs and the send directory name, and the two never cross.
- F-6 (minor) mcp-application/src/main/kotlin/dev/rectify/io/mcp/core/rpc/McpDispatcher.kt:149 — render() inlines `envelope.hierarchyXml` verbatim (the full verbatim uiautomator rawDump threaded in by T-2) with no size check anywhere in the diff — grep for 'truncat' across the new code returns nothing. The plan states this twice, as a perf-budget target and as the mitigation for a 'med/high' risk row ('above it the XML truncates with an explicit marker rather than failing the call'), and it is not among the eight accepted waivers. A dense 1080x2400 dump can reach that order of magnitude, and the whole document rides as one stdout line. Cheap fix: truncate hierarchyXml at the budget in render() and append an explicit marker.
- F-7 (minor) presentation-feature-mirror/src/desktopMain/kotlin/presentation/feature/mirror/core/crop/AwtCropEncoder.kt:30 — `frame.toAwtImage()` converts the ENTIRE frame to a BufferedImage on every encode() call, i.e. once per annotation, before getSubimage() throws all but the crop away — roughly 10 MB of transient ARGB raster per annotation at 1080x2400 (~30 MB of churn for the plan's three-annotation reference send) plus the copy time, on the critical path of the <=2s NFR-3 budget. Retained bytes are unaffected (the budget's '<= 2 HeldFrames' holds: currentHeld + currentFrozenHeld, and the conversions are garbage immediately), so this is throughput and GC pressure rather than a leak. The CropEncoder interface takes the bitmap per call, so the lazy fix is to memoize the converted image per frame identity inside AwtCropEncoder rather than to change the seam.
- F-8 (minor) presentation-feature-mirror/src/commonMain/kotlin/presentation/feature/mirror/core/send/SendProjection.kt:72 — Since AF-5 made the success path reduce SendPhase.Idle directly, nothing in production ever produces SendPhase.Sent — grep across main source sets shows it only in these two projection branches and in tests. The dead constant is cheap, but the prose around it is now wrong in three places a future reader will trust: SendProjection.kt:88-92 explains at length why 'SendPhase.Sent always wins over a dropped session' (a case that cannot occur), line 72/101 map a state that never arrives, and MirrorContent.kt:185-188 tells the reader the overlay 'includes the two TERMINAL phases ... so its last step reads Sent (green) or Sent (red)' when only the red one is reachable. The AC-19 waiver covers the missing animated progression; it does not cover KDoc that describes states the code can no longer enter. Either delete SendPhase.Sent or correct the three comments.
- F-9 (nit) presentation-feature-mirror/src/commonMain/kotlin/presentation/feature/mirror/source/mirror/MirrorViewModel.kt:661 — resolveAndSend() re-evaluates canSend(state) inside the reducer precisely so a stale dispatch cannot bypass the button; clearStaged() does not re-evaluate canClear and applies unconditionally. Harmless today (the envelope captures `frozen` by value before any suspension, so a Clear landing mid-send cannot corrupt the payload), but it is an asymmetry against TAC-2's own 'the guard a double-dispatch cannot bypass' framing, and F-2 is a path that makes the button reachable mid-flight.
- F-10 (nit) data-handoff-api/src/desktopMain/kotlin/data/handoff/api/core/slot/FileSlotAnnotationHandoff.kt:79 — I tried to break resolve()'s guard and could not, so this is a documentation nit rather than a defect. asBareName() rejecting blank, '/', '\\' and '..' is sufficient for the stated threat: a POSIX absolute path carries '/', a Windows one carries '\\' or an illegal ':' (InvalidPathException, caught by the dispatcher), a NUL byte is an InvalidPathException, unicode look-alikes such as U+FF0F are not path separators on any supported filesystem, and envelope.sentAtMs is a Long so the directory component cannot be influenced. What the guard does NOT cover is a symlink planted inside the send directory — the composed file:// URI is never normalized or checked against root, and the server hands the URI to the agent without resolving it. That requires write access to a 0700 directory, so it is correctly out of the threat model, but the security note's absolute phrasing ('the server never follows a path outside its own handoff root') is stronger than what the code proves. One `normalize().startsWith(root)` assertion would make the claim literal.
- F-11 (nit) data-handoff-api/src/desktopMain/kotlin/data/handoff/api/core/slot/FileSlotAnnotationHandoff.kt:49 — Only directories get explicit permissions (createOwnerOnlyDirectories). Files.write for the images and Files.writeString for latest.json.tmp both use the process umask, so the files are typically 0644 and latest.json keeps that mode through the ATOMIC_MOVE. In practice the 0700 directory bit is what protects them and it holds, because createDirectories applies the attribute to the root it creates on first publish. The gap is narrow: if ~/.rectify/handoff already exists with laxer permissions, createDirectories is a no-op on it and latest.json — which carries the whole prompt and the whole hierarchy dump — is left world-readable. The plan claims 'files rw-------'; the code never sets a file mode.
- F-12 (nit) presentation-feature-mirror/src/commonMain/kotlin/presentation/feature/mirror/source/mirror/MirrorContract.kt:554 — MirrorSideEffect.SendComplete.count has no production reader: RectifyWindow's showSendComplete uses only summary and sessionId, and the count is already baked into the summary string by toastLabel. It is referenced only by tests. Keep it if a second host is expected to format its own toast, otherwise it is one more field to keep in sync.
- F-13 (nit) mcp-application/src/main/kotlin/dev/rectify/io/mcp/source/entry/Main.kt:37 — writeFrame and logStderr are internal but live under source/entry; package-layout.md puts internal declarations in core/ and reserves source/ for the public surface. Only `main()` has to be in source/. Trivial, and the module has no explicitApi() to police it — noted for consistency with the rest of the repo, where this split is otherwise respected throughout the diff (core/send, core/crop, core/unsupported, core/slot all check out, and :data-handoff-api correctly has a core/ only because FileSlotAnnotationHandoff is internal).
- F-14 (nit) data-handoff-api/src/desktopMain/kotlin/data/handoff/api/core/slot/FileSlotAnnotationHandoff.kt:61 — Answering the 'prune vs concurrent read' question explicitly: the prune can delete a send directory whose file:// refs an agent received from an earlier get_latest_annotation call and has not dereferenced yet, so a tool result can go stale between the reply and the agent opening frame.png. This is inherent to the gate-approved single-slot, one-send-retention design and is not a defect to fix in F-7 — but it is a contract an MCP consumer needs to know about ('refs are valid until the next send'), and neither mcp-application/CLAUDE.md nor the tool description says so. One sentence in the tool description would do it.
