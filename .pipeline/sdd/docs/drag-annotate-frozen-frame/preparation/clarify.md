## Data

### overview

Implements the core drag-to-annotate workflow on top of F-1's shell and F-2's live mirror: dragging on the live mirror draws a dashed red selection box with a live device-pixel size readout and ruler guides; releasing freezes that frame and stages a numbered annotation; the frozen stage dims everything outside annotation boxes and opens a per-mark comment popover (autofocused, Enter to save, a delete control, a position meta line); crowded popovers relocate into the side panel's Notes tab as a gutter with leader lines. Almost every visual primitive this feature needs (AnnotationMark, CommentPopover, AnnotationPopover, Ruler, AnnotationRow, CounterBadge) already ships in presentation-core-ui — this spec assembles them, adds the coordinate-conversion plumbing the proof-of-concept already proved necessary, and wires the toolbar's two reserved slots plus the Notes tab.

### problemStatement

F-1/F-2 deliver a live mirror with no way to mark anything on it — a tester can only describe a bug in prose or attach a raw screenshot, which is exactly what this product exists to replace. rectify-poc proved the drag-box interaction is feasible but also documented a silent density-conversion bug (a rectangle landing `density`x from the cursor — 2x on this host's Retina display) that corrupts every annotation's position unless the conversion is made explicit and tested. No cached design comp illustrates any part of this interaction (all five are device-discovery screens), so every visual detail must be derived from existing shipped components or invented and named.

### purpose

Give the user a single drag gesture that freezes the moment they saw a bug, draws a box around it, and opens a focused place to describe it — stored in device-pixel coordinates that stay correct regardless of host density or window size.

### goals

- Reuse the already-shipped annotation kit components (AnnotationMark, CommentPopover, AnnotationPopover, Ruler, AnnotationRow, CounterBadge) rather than re-authoring visual primitives — presentation-core-ui already has ~115 components and F-1/F-2 both found 'assemble, don't author' to be the honest answer.
- Make the composable-dp / host-physical-px / device-screenshot-px conversion explicit, centralized in one pure function, and unit-tested, so the POC's documented density trap cannot silently regress.
- Wire the toolbar's stagedCounter and clearAction slots and the Notes tab — all three shipped as stubs/empty slots in F-1, explicitly reserved for this feature.
- Ship FR-9's gutter/leader-line relocation at minimum-demo fidelity so AC-9, already assigned to this spec by the approved PRD, is not silently dropped from the deliverable.

| FR-27 | Wire the toolbar's stagedCounter slot to the live staged-annotation count (CounterBadgeState.Empty at 0, Staged otherwise) and the clearAction slot to removing every staged annotation while leaving the stage frozen (not ending the session). |
| FR-28 | Fill the side panel's Notes tab with one AnnotationRow per staged annotation (index, comment or the empty-state copy, position meta line), kept in sync with the same staged-annotation list FR-27 wires to the toolbar; selecting a row selects the corresponding mark on the frame. |
| FR-29 | Scope annotation keyboard handling to the focused popover: Enter commits the comment text and keeps the annotation pinned; Escape collapses the popover back to a pinned, unselected mark without deleting it; the delete control (CommentPopover's existing close affordance, repurposed to mean delete per FR-8) removes the annotation and decrements the staged count. None of these three consume or bubble into the window-level Cmd+1/2/3 tab shortcut or the device picker's own Escape handler — both already key off disjoint event shapes (meta-modified keys vs. a focus subtree that cannot coexist with the frozen-frame stage). |
| FR-30 | On freeze, replace the live MirrorFrameView with a static render of the captured bitmap plus a dim/scrim treatment outside every annotation box, retain the device name in the existing toolbar/status chrome, and expose a 'Resume Live' control that discards the frozen frame and its staged annotations and returns the stage to live streaming. Freezing is a display-level snapshot only: the underlying sessionDeviceId-gated capture/transport loop is never paused or restarted, so resuming needs no new adb session. |
| FR-31 | While a frame is frozen, further drag-and-release gestures on the stage add additional staged annotations against the same frozen frame rather than re-triggering the freeze transition or replacing the captured bitmap. |

### outOfScope

- Measurement / measure-mode (F-5) — MeasureCard/MeasureMark exist in the kit but are not wired here.
- Payload preview (F-6) and MCP send (F-7) — the Payload tab and any network/export behaviour.
- Capture/annotation history (F-8) — multi-frame sessions; this spec holds exactly one frozen frame in memory at a time.
- Error cards (F-3).
- Device rotation / resolution change mid-annotation-session.
- The gutter/leader-line 8px elbow-stagger visual polish named in AnnotationPopover's KDoc (deferred — see survey Q5).
- Pausing the capture/transport loop while frozen for power/perf (FR-30 keeps it running; a later optimization pass may revisit).

### successMetrics

- Every drag-to-annotate action on the 2.0-density dev host lands the drawn box within 1px of the pointer (no density-trap regression).
- The existing 160+ desktop tests stay green; this spec adds tests rather than destabilizing them.

### openQuestions

- Whether to pause the capture/transport loop while frozen (power/perf optimization) is left for later — AS-13/FR-30 assume it keeps running.
- The gutter/leader-line 8px elbow-stagger visual polish named in AnnotationPopover's KDoc is not implemented in v1 — a follow-up design/visual-QA pass should revisit it.
- Whether a frozen frame should ever be allowed to persist annotations across a Resume-Live -> freeze-again cycle (i.e., multi-frame annotation sets) is explicitly deferred to F-8 (history).
